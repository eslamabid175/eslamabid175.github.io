Database Design

💡 Database lifecycle mindset: دراسة الـ database مش مجرد Models وORM. الرحلة الكاملة هي: فهم الدومين → تصميم العلاقات → كتابة migrations → حماية integrity → تحسين queries → متابعة الأداء والتغييرات مع الوقت.

Database Lifecycle Journey

01
Requirements
اعرف مين بيكتب البيانات، مين بيقرأها، وإيه الحالة الطبيعية ودورة الحياة لكل record.
02
Schema
اختار tables, foreign keys, many-to-many relations, choices, وحقول timestamps من البداية.
03
Constraints
أضف uniqueness, validation, immutable snapshots, وقواعد تمنع التكرار أو drift في البيانات.
04
Migrations
غير الـ schema بمسار واضح وآمن بدل التعديل اليدوي المباشر على الجداول.
05
Querying
راجع الـ read patterns الفعلية واستخدم select_related, prefetch_related, filtering, ordering, pagination.
06
Operations
تابع الأداء، أضف indexing بحساب، استخدم transactions وقت الحاجة، وراجع أثر كل migration قبل النشر.

1. تصميم قاعدة البيانات

قاعدة البيانات أصعب حاجة تتغير بعد ما المشروع يكبر، فتصميمها صح من الأول أهم من أي كود فوقها.

🧩
Normalization
كل معلومة تتخزن مرة واحدة، والباقي يشاور عليها بـ foreign key. لو اسم العميل متخزن جوه جدول الطلبات وغيّره، هتعدّل آلاف الصفوف، ولو نسيت صف هيبقى عندك اسمين لنفس الشخص.
📋
Denormalization
العكس عن قصد: تكرر معلومة عشان القراية تبقى أسرع، زي عمود comments_count على البوست بدل ما تعدّ التعليقات كل مرة. التمن إنك تحافظ على التزامن بنفسك.
📖
Indexes (B-tree)
من غير index الداتابيز بتقرا كل الصفوف (Seq Scan). الـ index نسخة مترتبة من العمود. اعمله على الأعمدة اللي بتتكرر في WHERE و JOIN و ORDER BY، مش على كل عمود.
↔️
Composite index — leftmost prefix
index على (status, created_at) بيخدم فلتر بـ status لوحده، أو status مع ترتيب بـ created_at، لكن مش بيخدم فلتر بـ created_at لوحده.

🎯 الهدف من الموضوع دا: إزاي توزّع الشغل على أجزاء، بحيث النظام يستحمل الضغط ويفضل شغال لو جزء فيه وقع.

1. ابدأ بالأرقام، وبعدين الـ Scaling

قبل أي تصميم، احسب الحمل؛ الأرقام هي اللي بتقولك محتاج تعقّد ولا لأ.

3. الطوابير والـ Rate limiting

الطابور بيحمي النظام من الذروة، والـ rate limiting بيحميه من الاستغلال.

📨
Message queues
بتفصل اللي بيطلب الشغل عن اللي بينفذه، بتمتص الذروة (١٠٠٠ مهمة دخلوا مرة واحدة والـ workers بيخلصوهم على مهلهم)، وبتسمح بإعادة المحاولة. Celery + Redis كفاية لأغلب المشاريع، و Kafka لما يبقى عندك events كتير لازم كذا خدمة تسمعها.

4. الـ CAP والـ Consistency

في أي نظام موزّع لازم تقرر: الأهم إن البيانات تبقى دقيقة دايمًا، ولا إن النظام يرد دايمًا؟

🎯
Consistency
كل قراية بتشوف آخر كتابة، حتى لو اضطريت ترفض الطلب. زي رصيد البنك.
🟢
Availability
كل طلب ياخد رد، حتى لو البيانات مش آخر نسخة. زي عدد الـ likes.
⏱️
Eventual consistency
النسخ هتتطابق، بس مش في نفس اللحظة. الـ read replica مثال، وتطبيق Flutter الـ offline اللي بيتزامن لما النت يرجع مثال تاني.
🧠 القرار مش للنظام كله: لو الشبكة اتقطعت بين أجزاء النظام (Partition) لازم تختار واحدة. وفي نفس التطبيق، الدفع ممكن يبقى consistent، والـ feed يبقى eventually consistent.
⚖️ الـ trade-off: حتى من غير انقطاع، فيه trade-off دايم بين السرعة والدقة: الـ read replica أسرع، بس ممكن تكون متأخرة.

🧪 اختبر نفسك

عدد الـ likes على بوست ورصيد محفظة: أنهي واحد تختار فيه Consistency، وأنهي Availability؟
الرصيد Consistency: الأحسن ترفض العملية من إنك تصرف فلوس مش موجودة. الـ likes Availability: لو العدد اتأخر ثواني محدش هيتضرر.
يعني إيه eventual consistency؟ اديني مثال من مشروع Flutter + Django.
إن النسخ المختلفة من البيانات هتتطابق، بس بعد شوية. أمثلة: الـ read replica، أو تطبيق Flutter الـ offline اللي بيتزامن مع السيرفر لما النت يرجع.

DevOps & Production

🎯 الهدف من الموضوع دا: الكود اللي مش في production مالوش قيمة، والكود اللي في production من غير مراقبة انت أصلًا مش عارف إذا كان شغال.

1. Docker للـ production

الـ image اللي بتروح production لازم تبقى صغيرة وآمنة، وبتتبني بنفس الطريقة كل مرة.

🏗️
Multi-stage build
مرحلة بتبني فيها المكتبات بأدوات الـ compile، ومرحلة نهائية خفيفة فيها اللي محتاجه بس.
👤
Non-root
لو حد اخترق الـ container، ما ياخدش صلاحيات كاملة.
🙈
.dockerignore
عشان .git و .env والـ media ما يدخلوش الـ image.
🧬
Image واحدة وأوامر مختلفة
نفس الـ image تشغّل gunicorn للـ web، و celery worker، و celery beat. والإعدادات من environment variables مش مكتوبة في الكود.
dockerfile FROM python:3.12-slim AS builder WORKDIR /app RUN apt-get update && apt-get install -y --no-install-recommends build-essential COPY requirements.txt . RUN pip wheel --no-cache-dir --wheel-dir /wheels -r requirements.txt FROM python:3.12-slim WORKDIR /app RUN useradd --create-home appuser COPY --from=builder /wheels /wheels RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels COPY . . USER appuser CMD ["gunicorn", "config.wsgi:application", "--bind", "0.0.0.0:8000"]
⚖️ الـ trade-off: build-essential موجود في مرحلة الـ builder بس، فالـ image النهائية أصغر وفيها أدوات أقل ممكن تتستغل، مقابل Dockerfile أطول شوية بمرحلتين.

🧪 اختبر نفسك

ليه الـ multi-stage build بيخلي الـ image أصغر وأأمن؟
لأن أدوات الـ compile زي build-essential بتفضل في مرحلة الـ builder وما بتدخلش الـ image النهائية. image أصغر يعني تنزيل و deploy أسرع، وأدوات أقل ممكن حد يستغلها لو اخترق الـ container.
ليه تشغّل الـ web والـ worker والـ beat من نفس الـ image؟
عشان الكود والمكتبات يبقوا نفس النسخة بالظبط في التلاتة. بتبني مرة واحدة، وكل container بيختلف في الأمر اللي بيشغّله بس.

2. الـ CI/CD

الـ CI بيمنع الكود البايظ يدخل، والـ CD بيخلي الـ deploy حاجة مملة ومتكررة، ودا بالظبط المطلوب.

01
CI مع كل PR
lint (ruff)، و tests، و build. الـ merge ممنوع لو فيه حاجة حمرا.
02
CD بعد الـ merge
build للـ image بـ tag هو الـ git SHA، و deploy على staging، و smoke tests، وبعدين production.
03
Rollback
كل image ليها tag، فالرجوع معناه deploy للـ tag اللي قبله.
yaml name: CI on: [pull_request] jobs: test: runs-on: ubuntu-latest services: postgres: image: postgres:16 env: POSTGRES_PASSWORD: postgres ports: ['5432:5432'] options: >- --health-cmd pg_isready --health-interval 10s --health-timeout 5s --health-retries 5 steps: - uses: actions/checkout@v4 - uses: actions/setup-python@v5 with: python-version: '3.12' - run: pip install -r requirements.txt - run: ruff check . - run: python manage.py test env: DATABASE_URL: postgres://postgres:postgres@localhost:5432/postgres
⚖️ الـ trade-off: postgres service في الـ CI أبطأ وأتقل من SQLite، بس الـ tests بتشتغل على نفس الداتابيز اللي في production، فما تخبّيش bugs في الـ constraints والـ locking والـ JSON fields.

🧪 اختبر نفسك

ليه الـ image بتاخد tag هو الـ git SHA مش latest؟
عشان كل image تبقى مربوطة بـ commit معين. تعرف بالظبط إيه اللي شغال في production، والـ rollback يبقى deploy للـ SHA اللي قبله.
ليه الـ CI فيه postgres service بدل SQLite في الـ tests؟
عشان الـ tests تشتغل على نفس الداتابيز اللي في production. فيه سلوك مختلف بينهم، زي الـ constraints والـ locking والـ JSON fields، و SQLite ممكن تخبّي bugs.

3. Migrations من غير ما production يقع

أثناء الـ deploy، النسخة القديمة والجديدة من الكود بيشتغلوا في نفس الوقت لدقايق. لو migration مسحت عمود، الكود القديم اللي لسه شغال هيقع.

نمط expand / contract

01
Expand
ضيف العمود الجديد nullable.
02
Dual write
deploy لكود بيكتب في القديم والجديد.
03
Backfill
انقل البيانات القديمة للعمود الجديد.
04
Read new
deploy لكود بيقرا من الجديد بس.
05
Contract
في deploy بعدها، امسح العمود القديم.
python from django.contrib.postgres.operations import AddIndexConcurrently from django.db import migrations, models class Migration(migrations.Migration): atomic = False # لازم مع CONCURRENTLY dependencies = [('orders', '0007_order_full_name')] operations = [ AddIndexConcurrently( model_name='order', index=models.Index(fields=['status', 'created_at'], name='order_status_created_idx'), ), ]
🔒 خلي بالك من الـ locks: إضافة index عادي على جدول كبير بتقفله وقت طويل. في PostgreSQL استخدم AddIndexConcurrently، والـ migration دي لازم يبقى فيها atomic = False.
⚖️ الـ trade-off: الـ expand/contract بياخد كذا deploy بدل migration واحدة، بس مفيش لحظة الكود القديم فيها بيدوّر على عمود مش موجود.

🧪 اختبر نفسك

ليه migration بتمسح عمود ممكن توقع production حتى لو الكود الجديد مش بيستخدمه؟
لأن أثناء الـ deploy الكود القديم لسه شغال على بعض السيرفرات وبيقرا العمود دا. أول ما الـ migration تمسحه، الطلبات اللي رايحة للكود القديم بتقع.
عايز تغيّر اسم عمود من name لـ full_name. اكتب الخطوات.
ضيف full_name nullable، و deploy كود بيكتب في الاتنين، وانقل البيانات القديمة، و deploy كود بيقرا من full_name بس. وبعد ما تتأكد، امسح name في deploy لوحده.

4. الـ Cloud: افهم المفاهيم، مش الشركة

أسامي الخدمات بتختلف من شركة للتانية، لكن المفاهيم واحدة؛ لو فهمتها هتعرف تشتغل على أي cloud.

🖥️
Compute
VMs، أو containers مُدارة زي Cloud Run و ECS.
🗄️
Managed database
الـ backups والـ failover والتحديثات عليهم. أغلى، بس لفريق صغير تقريبًا دايمًا تستاهل.
🪣
Object storage + CDN
للصور والملفات.
🌐
Networking
الداتابيز في private network، مش مكشوفة على الإنترنت.
🔐
IAM
كل خدمة تاخد أقل صلاحية محتاجاها.
⚖️ الـ trade-off: Kubernetes قوي جدًا، بس تمنه في التعقيد كبير، وأغلب المشاريع الصغيرة والمتوسطة مش محتاجاه. ونفس الفكرة مع الـ managed database: بتدفع أكتر مقابل إنك ما تديرش الـ backups والـ failover بإيدك.

🧪 اختبر نفسك

فريق من ٣ مطورين: تشغّل PostgreSQL بنفسك على VM ولا managed database؟
غالبًا managed. فرق الفلوس أقل بكتير من تمن الـ backups والتحديثات والـ failover لو عملتهم بإيدك، وغلطة واحدة فيهم ممكن تضيّع بيانات.
ليه الداتابيز تبقى في private network؟
عشان محدش من الإنترنت يقدر يوصل لها مباشرة، حتى لو الباسورد اتسرب. السيرفرات اللي جوه نفس الشبكة بس هي اللي تكلمها.

5. الـ Observability: تعرف المشكلة قبل العميل

الهدف إنك تعرف المشكلة قبل العميل، وتلاقي سببها بسرعة.

📝
Logs — إيه اللي حصل
خليها structured (JSON)، وفيها request_id يمشي مع الطلب من الـ web لحد الـ Celery task، فتتبع طلب واحد وسط ملايين.
📈
Metrics — كام ومرة قد إيه
راقب ٤ حاجات: الـ latency، وعدد الطلبات، ونسبة الأخطاء، ومدى امتلاء الموارد (CPU والذاكرة والـ connections).
🧵
Traces — الوقت راح فين
الطلب قضّى وقته فين بالظبط: في الداتابيز؟ ولا في API خارجي؟
🐞
Error tracking
Sentry في Django و Flutter، مربوط برقم الـ release.
📊 اقرا p95 وp99 مش المتوسط: متوسط 200ms ممكن يخبّي إن ٥٪ من المستخدمين بيستنوا ٣ ثواني.
⚖️ الـ trade-off: الـ alerts على كل حاجة بتطمّنك على الورق بس بتعلّم الفريق يتجاهلها. حطها على الأعراض اللي المستخدم بيحس بيها (الأخطاء زادت، الـ latency علي) بس.

🧪 اختبر نفسك

ليه p95 أهم من المتوسط؟
المتوسط بيخبّي الطلبات البطيئة وسط الكتير السريع. الـ p95 بيقولك إن ٥٪ من الطلبات أبطأ من الرقم دا، ودول مستخدمين حقيقيين بيحسوا بالبطء.
إيه فايدة الـ request_id في الـ logs؟
بيربط كل سطور الـ log الخاصة بطلب واحد، حتى لو اتوزعت على سيرفر الـ web والـ Celery worker. فتقدر تتبع مشكلة مستخدم معين من أولها لآخرها.
